# VeriFact

> **Verify what AI says.**

**Research Title**: *"VeriFact: A MetaQA-Based Framework for Detecting Fact-Conflicting Hallucinations in Large Language Models"*

VeriFact is an explainable hallucination-analysis system designed to evaluate factual consistency in answers generated by Large Language Models (LLMs). It analyzes AI-generated text using two independent, complementary verification branches:

1. **MetaQA-Based Metamorphic Verification**: A reference-free internal consistency engine that tests whether the model's belief remains stable under controlled semantic perturbations (meaning-preserving synonym mutations and meaning-reversing antonym mutations).
2. **Web Evidence Verification**: An external factual grounding engine that extracts verifiable claims from the answer, routes targeted searches through Tavily to authoritative domains, extracts clean claim-relevant evidence, and verifies claims strictly against retrieved sources.

Once both verification branches complete, their results are presented through an application-level **Overall VeriFact Assessment** that computes a balanced combined risk signal without modifying or corrupting the underlying research scores.

## Overview

### The Problem: Fact-Conflicting Hallucinations
Large Language Models frequently produce statements that sound confident, well-structured, and persuasive, but conflict with established real-world facts. These **fact-conflicting hallucinations** pose serious risks in education, medicine, law, research, and automated decision-making.

### Why Self-Reflection Fails
Asking an LLM *"Is your answer accurate?"* or *"Did you hallucinate?"* rarely works. Due to **self-confirmation bias**, **sycophancy**, and attention priors over previously generated tokens, models routinely defend and rationalize their own mistakes rather than identifying them.

---

## Why VeriFact?

Traditional hallucination detection either relies on expensive manual human fact-checking or naive self-evaluations. VeriFact addresses these challenges by combining:

1. **Internal Cognitive Stability (MetaQA)**: Testing whether the model's internal belief is robust or brittle when phrased in logically equivalent or contradictory forms.
2. **External Ground Truth (Web Evidence)**: Grounding factual claims in external authoritative documentation retrieved from the web.
3. **Transparent Explanations**: Avoiding black-box confidence numbers by displaying the exact mutations, verifier rationales, clean evidence summaries, source URLs, and signal relationships.

---

## Core Idea

VeriFact separates the **research methodology** from the **application-level engineering**:

- **Research Core (MetaQA)**: A metamorphic testing framework that introduces controlled semantic variations to test factual consistency without external data.
- **Additional Capability (Web Evidence)**: An independent retrieval-augmented fact-checking pipeline that audits claims against real-world sources.
- **Application-Level Fusion (Overall Assessment)**: An engineering synthesis layer that provides users with an instant summary verdict and combined risk score without modifying the underlying branch algorithms.

---

## Multi-Model VeriFact Architecture (Phase 1)

VeriFact supports dynamic multi-model evaluation across five leading cloud models. Rather than fixing one model permanently as generator and others as verifiers, the user selects the **Answer Model**:

- **Dynamic Answer Generation**: The selected model generates the candidate answer.
- **Dynamic Verifier Pool**: All other available models automatically become independent cross-model verifiers (the selected model is strictly excluded from its own verifier pool).
- **100% Cloud-Based Inference**: VeriFact uses cloud/API-based LLM inference. Gemma 4:26B is accessed through Ollama Cloud; no local Ollama installation is required. There are no calls to `localhost:11434`.
- **Independent Verification**: Verifiers independently judge consistency. Verifiers are never given expected verdicts, scores, or ground-truth labels.
- **Scientific Caveat**: Model agreement across independent verifiers is an indicator of consistency and robustness, **not absolute ground truth**.

## Answer Generation & Provider Routing

- **Dynamic Model Selection**: Select any configured cloud model as the primary answer generator from the Detect UI or via the API (`answer_model: "gemma"`).
- **Default Answer Model**: **Gemma 4:26B**, accessed through the official **Ollama Cloud API** (`https://ollama.com/api`), not local daemon inference.
- **Exclusion Guarantee**: When model $M$ is chosen as the answer model, the verifier pool is dynamically computed as $\text{AllModels} \setminus \{M\}$. Model $M$ will never judge its own answer.
- **Provider Isolation**: Provider-specific HTTP and payload mechanics are isolated within dedicated clients (`OllamaCloudClient`, `CloudflareClient`, `GroqClient`, `OpenRouterClient`, `GeminiClientAdapter`).
- **Immediate Answer Return**: The generated answer is saved to SQLite with status `answer_ready` and returned to the UI immediately, displaying the model and cloud provider badge. Users can read the answer while both verification branches proceed in parallel.

## MetaQA Methodology

MetaQA reframes hallucination detection as a metamorphic software testing problem. It evaluates an LLM's consistency under controlled semantic perturbations:

1. **Candidate Answer**: The base answer produced by the generator model.
2. **Metamorphic Perturbation**: Generating statements derived from the answer's core claims:
   - **Synonym Mutations (Meaning-Preserving)**: Restate the factual claim using different phrasing, vocabulary, or active/passive structure. Expected relationship = **`YES`** (consistent).
   - **Antonym Mutations (Meaning-Reversing)**: Invert, negate, or substitute entities to create a factual contradiction of the original claim. Expected relationship = **`NO`** (contradiction).
3. **Independent Verification**: Google Gemini independently verifies each mutation against the question and original answer.
   - **Crucial Invariance**: The verifier is **never told** whether a mutation is a synonym or antonym, and is **never given** the expected verdict.
4. **Observed Verdicts**:
   - **`YES`**: The mutation is factually consistent with the original answer.
   - **`NO`**: The mutation contradicts or conflicts with the original answer.
   - **`NOT SURE`**: The relationship cannot be reliably determined from the text.

---

## MetaQA Scoring

Scoring is 100% deterministic and calculated mathematically in Python (not graded by an LLM prompt):

| Mutation Type | Observed `YES` | Observed `NO` | Observed `NOT SURE` |
| :--- | :---: | :---: | :---: |
| **Synonym** (Expected `YES`) | **0.0** (Consistent) | **1.0** (Violation) | **0.5** (Uncertain) |
| **Antonym** (Expected `NO`) | **1.0** (Violation) | **0.0** (Consistent) | **0.5** (Uncertain) |

The total **MetaQA Hallucination Score** $H$ is the arithmetic mean of all mutation contributions:

$$H = \frac{1}{N} \sum_{i=1}^{N} c_i \quad \text{where } H \in [0.0, 1.0]$$

- **Lower Score ($H \to 0.0$)**: The model's behavior aligns with metamorphic expectations; few or no consistency violations detected.
- **Higher Score ($H \to 1.0$)**: The model readily accepts contradictions or rejects equivalent paraphrases; strong indication of hallucination.
- **Classification**: Governed by configured threshold $\theta$ (default $\theta = 0.5$):
  - $H < \theta \implies \textbf{Reliable}$
  - $H \ge \theta \implies \textbf{Hallucinated}$

## Mutation Generation Optimization

To make interactive detection fast and responsive, the mutation pipeline incorporates several key engineering optimizations:

- **Eliminated Separate LLM Claim Extraction**: In early prototypes, a dedicated LLM call was made solely to split the answer into claims. The current pipeline uses deterministic sentence and entity parsing in 0ms (`fallback_claims_from_answer`), removing a full LLM roundtrip.
- **Single-Request Generation**: Synonym and antonym mutations are generated together in a single structured LLM call rather than sequential requests.
- **Optimized Token Budget**: The mutation generation request uses a tight token cap (`LLM_MUTATION_MAX_TOKENS=300`) to minimize generation latency while ensuring complete sentences.
- **Ollama Keep-Alive**: Uses `OLLAMA_KEEP_ALIVE=30m` so model weights remain memory-resident between runs.
- **Configured Counts**: The interactive Detect pipeline defaults to **3 synonym** and **3 antonym** mutations (6 total mutations per run).

## Gemini Verifier

- **Cross-Model Architecture**:
  - **Answer Generation**: Ollama / Gemma 4:26B
  - **Mutation Generation**: Ollama / Gemma 4:26B
  - **Mutation Verification**: Google Gemini (`gemini-3.8-flash` via official `google-genai` SDK)
- **Isolated Context**: Gemini receives only the question, candidate answer, and mutation statement. It outputs structured JSON with a strict verdict (`YES`, `NO`, or `NOT SURE`) and rationale.
- **Technical Failures vs. Uncertainty**:
  - If Gemini encounters an API error, rate limit, timeout, or malformed JSON, the system marks `parse_failed=True, error=...`.
  - Technical failures are **never** treated as valid `NOT SURE` judgments.
- **No Silent Fallback**: If Gemini credentials are missing or the API is unavailable, the MetaQA verifier reports `UNAVAILABLE` rather than silently substituting the local generator model.

## Web Evidence Pipeline

Web Evidence audits claims against real-world web sources retrieved in real time:

1. **Claim Extraction**: Extracts independent factual assertions from the candidate answer while discarding greetings, formatting, and filler phrases.
2. **Question-Type Classification**: Rule-based classifier categorizes the question (e.g., General Facts, Science, Government, Current Events, Medicine).
3. **Authoritative Domain Strategy**: Recommends high-credibility domains matching the question category to guide retrieval.
4. **Tavily Search**: Queries Tavily Basic Search with focused queries per claim, respecting credit and concurrency limits.
5. **Evidence Extraction**: Cleans raw search results into concise, claim-specific evidence summaries.
6. **Snippet Verification**: Evaluates each claim strictly against retrieved evidence text.
7. **Verdict & Scoring**: Assigns verdicts and calculates the Web Evidence Consistency Score.

---

## Web Search & Targeted Routing

VeriFact uses [Tavily Search](https://tavily.com) configured for factual verification:

- **Query Generation**: Converts each extracted claim into a targeted search query.
- **Budget Limits**: Constrained by `WEB_MAX_CLAIMS=3`, `WEB_MAX_SEARCHES=3`, and `WEB_RESULTS_PER_CLAIM=2`.
- **Category-Based Domain Guidance**: Prioritizes encyclopedic, governmental (`.gov`), academic (`.edu`), and primary science sources depending on question type.
- **Not a Truth Oracle**: Domain preferences improve retrieval signal quality, but claims are verified strictly against the retrieved textual evidence.

---

## Claim-Relevant Evidence Extraction

A common issue in automated fact-checking is presenting raw search snippets cluttered with navigation bars, markdown headers, FAQ lists, and truncated text.

VeriFact solves this with **claim-relevant evidence extraction**:
- Raw snippets are preprocessed to strip markdown headers (`#`, `##`), navigation menus, Wikipedia citation brackets (`[1]`), and question headers.
- The pipeline scores sentences based on claim entity overlap and keywords to extract the exact 1–2 sentences that directly address the claim.
- Clean evidence summaries (`evidenceSummary`) are surfaced directly inside source cards alongside the source domain, title, URL, and verifier reasoning.

## Web Evidence Verdicts & Scoring

Each claim receives one of three verdicts:

- **`SUPPORTED`**: The retrieved evidence affirms the factual assertion of the claim.
- **`CONTRADICTED`**: The retrieved evidence directly conflicts with the factual assertion.
- **`INSUFFICIENT_EVIDENCE`**: The retrieved sources do not contain enough relevant information to prove or disprove the claim.

> [!IMPORTANT]
> **Insufficiency Is Not Hallucination**:
> If a niche or obscure claim cannot be verified due to search limitations or paywalls, it is labeled `INSUFFICIENT_EVIDENCE`. The system **never** assumes an unverified claim is a hallucination.

### Web Evidence Consistency Score
The score measures evidence support across checked claims:

$$\text{Web Consistency Score} = \frac{1}{N} \sum_{i=1}^N c_i \quad \text{where } c_i \in \{1.0 \text{ (Supported)}, 0.5 \text{ (Insufficient)}, 0.0 \text{ (Contradicted)}\}$$

- **1.00**: All checked claims are strongly supported by external evidence.
- **Lower**: Contradictions detected or evidence is insufficient.
- **Meaning**: This is an evidence coverage and consistency metric—it is **not** a calibrated probability of truth.

## Overall VeriFact Assessment

The **Overall VeriFact Assessment** is an application-level synthesis layer that unites both independent verification branches into a single clean summary card.

> [!NOTE]
> The Overall Assessment is a VeriFact engineering feature. It is **not** part of the original MetaQA or ClaimCheck research papers, which treat consistency and web fact-checking as separate paradigms.

### Assessment Verdicts & Decision Rules

1. **`Likely Reliable`**: MetaQA detected no consistency violations ($H < 0.5$) and web evidence supports checked claims without contradictions.
2. **`Potentially Hallucinated`**: One or more claims are contradicted by web evidence, or MetaQA detected consistency violations ($H \ge 0.5$) with contradictions or insufficient evidence.
3. **`Needs Verification`**: Signals point in differing directions (e.g., MetaQA is inconsistent but web evidence is supportive, or web evidence is partially supported/insufficient).
4. **`Insufficient Evidence`**: Web evidence was insufficient to verify claims, and MetaQA was unavailable.
5. **`Unavailable`**: Neither verification pipeline could be executed.

---

## Combined Hallucination Risk

To provide users with a single risk indicator without altering the branch metrics, VeriFact calculates an application-level **Combined Hallucination Risk**:

1. **Web Evidence Hallucination Risk**: Inverts the Web Evidence Consistency Score so that higher values represent higher risk:
   $$\text{Web Risk} = 1.0 - \text{Web Evidence Consistency Score}$$
2. **Combined Risk Formula**: Equi-weighted combination of MetaQA score and Web Risk:
   $$\text{Combined Hallucination Risk} = 0.5 \times \text{MetaQA Score} + 0.5 \times \text{Web Risk}$$

### Important Distinction
- **What it is**: An application-level heuristic signal combining internal metamorphic stability and external evidence consistency.
- **What it is NOT**: It is **not** a calibrated statistical probability of hallucination, nor proof that an answer is objectively true or false.

## Progressive Detection Flow

1. User submits a factual question on the Detect page.
2. Backend generates the answer via Ollama/Gemma and saves the run with status `answer_ready`.
3. The frontend renders the answer immediately.
4. MetaQA and Web Evidence start concurrently as background tasks via `asyncio.gather`.
5. Frontend polls `GET /api/runs/{id}` to display progress:
   - MetaQA shows mutation generation and Gemini verification progress.
   - Web Evidence shows question classification, search, and evidence verification progress.
6. When both complete, the compact **VeriFact Result** card displays the final verdict, combined risk score, 3-column score summary, and detailed findings below.

## Research Foundation

VeriFact builds upon and acknowledges two core research foundations:

1. **MetaQA Methodology**:
   > *"Hallucination Detection in Large Language Models with Metamorphic Relations"*
   > ACM Transactions on Software Engineering and Methodology (TOSEM)
   > DOI: [10.1145/3715735](https://doi.org/10.1145/3715735)
   > *VeriFact implements the metamorphic synonym/antonym mutation testing and arithmetic contribution scoring formulated in MetaQA.*

2. **Web Evidence Inspiration**:

## Performance & Engineering Decisions

- **Deterministic Preprocessing**: Extracts answer claims in 0ms using string heuristics rather than an expensive preparatory LLM call.
- **Combined Mutation Generation**: Requests synonym and antonym mutations together to halve inference overhead.
- **Bounded Concurrency**: Gemini requests run with concurrency caps (`GEMINI_VERIFY_CONCURRENCY=3`) to respect API rate limits.
- **Strict Token Limits**: Output tokens are capped per stage (e.g., 300 for mutations, 160 for evidence verification) to prevent runaway generations.
- **Memory-Resident Weights**: Ollama keep-alive keeps Gemma loaded in VRAM/RAM for 30 minutes, avoiding model reloads between queries.

---

## Security & Secrets

- **No Secrets in Frontend**: `GEMINI_API_KEY` and `TAVILY_API_KEY` reside exclusively in the backend `.env` file and are never sent to the client or embedded in client-side bundles.
- **No Git Leakage**: `.env` is ignored in `.gitignore`. Real credentials must never be committed.
- **Safe Public Settings**: `/api/settings` exposes only non-sensitive metadata (model names, provider types, counts).

## Limitations

- **Consistency Is Not Physical Truth**: MetaQA evaluates internal semantic stability. If an LLM consistently holds and defends a popular misconception, MetaQA may classify it as consistent.
- **Search Dependency**: Web Evidence accuracy is constrained by search engine index quality and domain access.
- **Insufficiency Nuance**: `INSUFFICIENT_EVIDENCE` denotes lack of retrieved data, not affirmative hallucination.
- **Hardware Demands**: Local inference with 26B parameter models requires adequate RAM and GPU acceleration for low latency.
- **Uncalibrated Metric**: The Combined Hallucination Risk is an engineering fusion metric, not a mathematically calibrated probability.
