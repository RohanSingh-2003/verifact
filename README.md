# VeriFact

> **Verify what AI says.**

**Research Title**: *"VeriFact: A MetaQA-Based Framework for Detecting Fact-Conflicting Hallucinations in Large Language Models"*

VeriFact is an explainable, dual-pipeline hallucination detection and analysis system designed to evaluate factual consistency in answers generated by Large Language Models (LLMs). Rather than relying on naive self-reflection (which suffers from self-confirmation bias and sycophancy), VeriFact analyzes AI-generated text using two independent, complementary verification branches:

1. **MetaQA-Based Metamorphic Verification**: A reference-free internal consistency engine that evaluates whether a model's underlying knowledge state remains stable under controlled semantic perturbations (meaning-preserving synonym mutations and meaning-reversing antonym/negation mutations), verified independently by cross-model verifiers.
2. **Web Evidence Verification**: An external factual grounding engine that extracts testable claims from the generated answer, routes targeted search queries through Tavily to authoritative domains, extracts clean claim-relevant evidence, and verifies claims strictly against retrieved source text.

Once both verification branches conclude, an application-level **Overall VeriFact Assessment** synthesizes a combined risk signal and executive verdict without modifying or corrupting the underlying research scores.

## Overview & Problem Statement

### The Problem: Fact-Conflicting Hallucinations
Large Language Models (LLMs) frequently generate answers that appear articulate, authoritative, and grammatically impeccable, yet conflict with established real-world facts. These **fact-conflicting hallucinations** pose critical risks in high-stakes applications including healthcare, law, education, software engineering, and automated research.

### Why Self-Reflection Fails
Asking an LLM *"Is your previous answer accurate?"* or *"Did you hallucinate?"* is empirically ineffective:
- **Self-Confirmation Bias**: Models exhibit disproportionate confidence in tokens they have already sampled into their generation context.
- **Sycophancy & Prior Reinforcement**: If a false premise or incorrect entity is introduced, the model tends to elaborate upon and rationalize the falsehood rather than refute it.
- **Superficial Fluency**: High language generation fluency masks brittle or fabricated internal factual associations.

### The VeriFact Solution
VeriFact separates the problem into two distinct, rigorous verification vectors:
1. **Internal Cognitive Consistency (MetaQA)**: Testing whether the model's factual commitments remain invariant when restated as synonyms, and are actively rejected when inverted as antonyms.
2. **External Factual Grounding (Web Evidence)**: Retrieving authoritative external documents from the web and strictly checking whether each claim is affirmed or refuted by independent textual evidence.
3. **Decoupled Architecture**: Returning candidate answers immediately to users (`answer_ready`), then executing verification pipelines asynchronously in parallel.

### Frontend–Backend Communication Flow
1. **Reverse Proxying**: In local development, the Vite frontend development server (`http://localhost:5173`) proxies all requests starting with `/api` directly to the FastAPI backend (`http://127.0.0.1:8000`). This avoids Cross-Origin Resource Sharing (CORS) complications during development.
2. **Immediate Handshake**: When a user submits a question on the Detect page, the frontend issues `POST /api/detect` with the question and the user-selected `answer_model`.
3. **Instant Response**: The backend synchronously generates the candidate answer, persists a run with status `answer_ready`, schedules verification background tasks, and immediately returns the answer JSON. The UI renders the answer in seconds.
4. **State Polling**: The frontend initiates polling on `GET /api/runs/{id}` (every 1,000ms). As background workers update SQLite, the frontend progressively renders:
   - Mutation generation status (`generating_mutations` → `mutations_ready`)
   - Individual mutation verification progress (`verifying_mutations`)
   - Web Evidence stages (`classifying_question` → `searching_web` → `verifying_evidence`)
   - Final Overall VeriFact Assessment and Combined Hallucination Risk once both branches finish.

## Main Features

### A. Answer Generation

Answer generation produces the primary factual text being audited.

- **Fixed Answer Generator**:
  - **Permanent Model**: **Gemma 4:26B** (`gemma4:26b`).
  - **Provider**: Official **Ollama Cloud API** (`https://ollama.com/api`) configured via `OLLAMA_API_KEY`.
  - **Permanent Configuration**: Gemma 4:26B is fixed as the sole answer-generating model in backend configuration. The model-selection dropdown has been removed from the user interface, and all user questions are answered by Gemma. No parameter or frontend state can override it, and no silent fallback to other models is permitted.
  - **100% Cloud Architecture**: VeriFact uses cloud/API-based inference over HTTPS with Ollama Cloud. **No local Ollama daemon or local GPU hardware is required**.
  - **Reasoning Control (`think: false`)**: The `OllamaCloudClient` enforces `think: false` so output is concise and deterministic within the configured token budget (`LLM_ANSWER_MAX_TOKENS=350`).
- **Decoupled Lifecycle**:
  - The answer is saved to SQLite with status `answer_ready` along with generation latency (`answer_ms`).
  - The answer text is returned immediately to the frontend. Answer generation never waits for metamorphic mutations, independent verifiers, or web searches.

### B. MetaQA-Based Hallucination Detection

MetaQA evaluates internal semantic stability by applying metamorphic testing principles to natural language claims.

- **Multi-Model Mutation Verification Stage**:
  - The model that generated the base answer (Gemma) is **strictly excluded** from verifying mutations.
  - The **multi-model verifier pool** (`Gemini 3.8 Flash`, `GLM-4.7-Flash`, `Qwen-2.5-32B`, `Liquid/OpenRouter`) acts directly as the **mutation verifier stage inside the MetaQA pipeline** (`metaqa/multi_verifier.py::verify_all_mutations_multi_model`).
  - Every individual mutation is evaluated concurrently across all available non-Gemma verifier models.
- **Metamorphic Mutation Generation**:
  - Core factual claims are parsed from Gemma's answer using strict JSON schemas.
  - Gemma produces paired mutations in a single token-capped call (`LLM_MUTATION_MAX_TOKENS=300`):
    - **Synonym Mutations (Meaning-Preserving)**: Paraphrased statements retaining original truth conditions. Expected verdict: **`YES`** (consistent).
    - **Antonym Mutations (Meaning-Reversing / Negation)**: Statements where a core entity, action, or date is negated to contradict the original assertion. Expected verdict: **`NO`** (contradicts).
  - Defaults: 3 synonyms + 3 antonyms (6 total mutations per interactive Detect run).
- **Prompt Isolation & Zero Leakage**:
  - Verifiers receive only: the original question, candidate answer, and the single mutated statement.
  - Verifiers are **never told** whether the statement is a synonym or an antonym.
  - Verifiers are **never told** the expected verdict, scoring thresholds, or ground-truth answers.
- **Verifier Responses & Technical Isolation**:
  - **`YES`**: Mutation is factually consistent with the candidate answer.
  - **`NO`**: Mutation conflicts with or is unsupported by the candidate answer.
  - **`NOT SURE`**: Semantic relationship cannot be reliably determined.
  - **Error Isolation**: Malformed responses or timeouts are flagged as `parse_failed=True` and isolated as technical errors—they are **never** counted as legitimate `NOT SURE` judgments. In multi-verifier mode, failed calls are excluded from penalty averaging so transient provider errors do not fabricate false penalties.
- **Deterministic Python Scoring**:
  - Scoring is calculated purely in Python using a strict metamorphic contribution matrix:

  | Mutation Type | Observed: `YES` | Observed: `NO` | Observed: `NOT SURE` |
  | :--- | :---: | :---: | :---: |
  | **Synonym** (Expected `YES`) | **0.0** (Consistent) | **1.0** (Violation) | **0.5** (Uncertain) |
  | **Antonym** (Expected `NO`) | **1.0** (Violation) | **0.0** (Consistent) | **0.5** (Uncertain) |

  - The aggregate **MetaQA Hallucination Score** $H$ is the arithmetic mean of all mutation contributions:
    $$H = \frac{1}{N} \sum_{i=1}^N c_i \quad \text{clamped to } [0.0, 1.0]$$
  - Threshold classification ($\theta = 0.5$ default):
    - $H < \theta \implies \textbf{Reliable}$
    - $H \ge \theta \implies \textbf{Hallucinated}$
- **Limitations of MetaQA**:
  - MetaQA measures **internal semantic stability**, not physical ground truth. If a model consistently believes and defends a widespread misconception under both synonym and antonym forms, MetaQA will record it as consistent ($H \to 0.0$).

### C. Direct-Answer Multi-Model Review

Concurrently with MetaQA, all configured non-Gemma models independently evaluate Gemma’s generated answer directly (`_continue_independent_verdicts` in `app/services/independent_verifiers.py`).

- **Input Context**: Each model receives the original user question, Gemma’s generated answer, extracted key claims, mutation context, and external web evidence snippets.
- **Independent Verdicts**: Each verifier outputs a structured evaluation:
  - **Verdict**: `Correct`, `Incorrect`, or `Uncertain`
  - **Reasoning**: Concise assessment explanation
  - **Contradictory Claims**: Specific statements identified as false or unsupported
  - **Confidence**: Numerical score only when meaningful
- **Consensus Aggregation**:
  - Aggregated into `MultiModelVerificationSummary`: `Consensus Correct`, `Consensus Incorrect`, `Disagreement`, or `Inconclusive`.
  - Disagreements and contradictory statements are explicitly highlighted in the UI.
  - **Decoupled from MetaQA**: Multi-model consensus is a complementary peer-review signal and **does not modify or replace the MetaQA Inconsistency Score**.

---

### D. Web Evidence Grounding

The Web Evidence pipeline provides external factual grounding by querying real-world documents in real time.

- **Claim Extraction**:
  - Independent factual claims are parsed from the candidate answer while stripping salutations, rhetorical questions, opinions, and markdown styling.
  - Budgeted by `WEB_MAX_CLAIMS=3` to ensure low latency and respect search quotas.
- **Question-Type Classification & Domain Strategies**:
  - A rule-based classifier categorizes questions into domains (e.g., General Facts, Science & Space, Government & Policy, Current Events, Statistics, Technology, Medicine, Academic Research).
  - Routes queries to authoritative high-credibility domains (e.g., `.gov`, `.edu`, Britannica, WHO, NASA, PubMed, Reuters). If preferred domains yield empty results, search automatically broadens.
- **Tavily Search API**:
  - Executes targeted search queries per claim using Tavily Basic Search.
  - Constrained by `WEB_MAX_SEARCHES=3` and `WEB_RESULTS_PER_CLAIM=2`.
- **Claim-Relevant Evidence Extraction**:
  - Raw snippets frequently contain HTML navigation bars, markdown headers, and Wikipedia citations (`[1]`).
  - VeriFact preprocesses snippets and extracts the concise 1–2 sentences directly addressing the claim (`evidenceSummary`), displaying them alongside source title, URL, and verifier reasoning.
- **Claim Verdicts & Scoring**:
  - Claims receive one of three strict verdicts:
    - **`SUPPORTED`**: External evidence explicitly affirms the claim.
    - **`CONTRADICTED`**: External evidence directly conflicts with the claim.
    - **`INSUFFICIENT_EVIDENCE`**: Retrieved snippets lack sufficient detail to confirm or refute.
  - **Invariance Principle**: Insufficient evidence is **never** treated as a hallucination. Unverified niche claims remain `INSUFFICIENT_EVIDENCE`.
  - **Web Evidence Consistency Score**:
    $$\text{Web Consistency Score} = \frac{1}{N} \sum_{i=1}^N c_i \quad \text{where } c_i \in \{1.0 \text{ (Supported)}, 0.5 \text{ (Insufficient)}, 0.0 \text{ (Contradicted)}\}$$
- **Strict Separation from MetaQA**:
  - Web Evidence is an external retrieval audit. Its consistency score is maintained as an independent metric and is **never** merged into or averaged with the MetaQA metamorphic score.

### D. Performance Evaluation & Benchmarks

VeriFact includes a dedicated evaluation module for measuring hallucination detection accuracy against gold-standard reference datasets.

- **Benchmark Module Architecture**:
  - Implemented in `backend/app/evaluation/` (`evaluator.py`, `dataset_loader.py`, `ground_truth.py`, `metrics.py`).
  - Supports dataset formats in JSON and CSV located in `backend/data/datasets/`.
  - Bundled dataset: `pilot.json` (40 hand-selected factual questions across 5 categories: `named_entity`, `location`, `date`, `numeric`, `general_fact`, 8 items each) accompanied by `pilot.manifest.json`.
- **Ground Truth & Review Handling**:
  - Evaluates candidate answers against dataset reference answers and acceptable aliases.
  - Ambiguous or subjective items are flagged as `needs_review=True` (e.g., items `q032` and `q039` in the pilot dataset).
  - Items flagged `needs_review` are preserved in stored results for auditability but are strictly excluded from automated Precision, Recall, and F1 calculations (leaving 38 labeled items).
- **Computed Evaluation Metrics**:
  - Accuracy, Precision, Recall, F1 Score, Specificity, False Positive Rate (FPR), False Negative Rate (FNR).
  - Full confusion matrix counts: True Positives (TP), True Negatives (TN), False Positives (FP), False Negatives (FN).
  - Category-by-category performance breakdowns.
  - Threshold sensitivity sweeps ($\theta \in [0.10, 0.90]$).
- **Persistence & Export**:
  - Evaluation runs are persisted to SQLite across `EvaluationRun`, `EvaluationResult`, and `EvaluationMetric` tables.
  - Complete evaluation records are exportable via `GET /api/evaluations/{id}/export` as downloadable CSV files.
- **Distinction Between Benchmarks and Live Detection**:
  - **Live Detection**: Interactive, end-to-end user query pipeline combining cloud LLM answer generation, metamorphic perturbations, and real-time Tavily search.
  - **Offline Evaluation**: Automated batch benchmarking running a fixed detector over pre-labeled question sets to measure classification efficacy against known reference facts.
- **Historical Results & Accurate Experiment Status**:
  - **Locked Research Run**: The frozen artifact in `experiments/results/58baff20-fb86-4f43-b20e-895a086ceb6b` represents a 40-question 2×2 study executed in **`mock` mode (DEMO / MOCK DATA)** using deterministic mock clients (`model-a`, `model-b`).
  - **Unexecuted Live 2×2 Study**: The intended live 2×2 configuration documented in `experiments/config/final_experiment.yaml` (`gpt-4o-mini` vs. `gpt-4o`) was **frozen as NOT EXECUTED** due to missing live API credentials. No live 2×2 experiment was run.
  - Incomplete or mock runs must never be cited as live multi-model empirical findings.

## Overall Assessment & Combined Risk

To assist human evaluators without corrupting the underlying research data, VeriFact provides an application-level synthesis layer:

1. **Overall VeriFact Assessment Verdicts**:
   - **`Likely Reliable`**: MetaQA detected no consistency violations ($H < 0.5$) and external web evidence supports checked claims without contradictions.
   - **`Potentially Hallucinated`**: Web evidence contradicts one or more claims, or MetaQA detected consistency violations ($H \ge 0.5$) with contradictory or insufficient evidence.
   - **`Needs Verification`**: Branch signals diverge (e.g., model is internally consistent but external sources are mixed/insufficient, or vice versa).
   - **`Insufficient Evidence`**: Web evidence was inconclusive and MetaQA was unavailable.
   - **`Unavailable`**: Neither branch could be executed.
2. **Combined Hallucination Risk Formula**:
   $$\text{Web Risk} = 1.0 - \text{Web Consistency Score}$$
   $$\text{Combined Hallucination Risk} = 0.5 \times \text{MetaQA Score} + 0.5 \times \text{Web Risk}$$
   - **Heuristic Disclaimer**: Combined Hallucination Risk is an application-level engineering heuristic combining internal stability and external evidence consistency. It is **not** a calibrated statistical probability.

## Installation & Setup

### Prerequisites
- **Python**: Version 3.11, 3.12, or 3.14 (64-bit)
- **Node.js**: Version 20 or higher, with `npm`
- **Git**: For cloning the repository
- **API Keys** (for live execution):
  - At least one cloud LLM API key (e.g., `OLLAMA_API_KEY` for Gemma or `GEMINI_API_KEY` for Gemini)
  - Tavily Search API key (`TAVILY_API_KEY`) for external web evidence grounding
  - *Note: For offline development and testing, `LLM_MODE=mock` requires zero API keys.*

### 1. Clone Repository
```bash
git clone https://github.com/RohanSingh-2003/verifact.git
cd verifact
```

### 2. Backend Setup
Open a terminal in the project root:

```bash
cd backend

# Create virtual environment
python -m venv .venv

# Activate virtual environment
# Windows PowerShell:
.\.venv\Scripts\Activate.ps1
# macOS / Linux:
# source .venv/bin/activate

# Install backend dependencies
pip install -r requirements.txt

# Create local environment configuration from template
copy .env.example .env
# (On macOS/Linux: cp .env.example .env)
```

### 3. Frontend Setup
In a second terminal:

```bash
cd frontend

# Install Node dependencies
npm install
```

### 4. Environment Variables Configuration
Edit `backend/.env` with your actual settings. Safe placeholders are provided below:

```env
# Application Settings
ENVIRONMENT=development
FRONTEND_ORIGIN=http://localhost:5173
DATABASE_URL=sqlite:///./data/verifact.db

# Execution Mode: "live" (Cloud APIs) or "mock" (offline test fixtures)

# 1. Gemma 4:26B via Ollama Cloud (Default Generator)
OLLAMA_API_KEY=your_ollama_cloud_api_key_here
OLLAMA_CLOUD_BASE_URL=https://ollama.com/api
OLLAMA_CLOUD_MODEL=gemma4:26b

# 2. Google Gemini API (Primary Cross-Model Verifier)

# 3. Optional Additional Cloud Providers

CLOUDFLARE_ACCOUNT_ID=your_cloudflare_account_id_here
GROQ_API_KEY=your_groq_api_key_here
OPENROUTER_API_KEY=your_openrouter_api_key_here

# 4. Web Evidence Grounding (Tavily Search API)
TAVILY_API_KEY=your_tavily_api_key_here
```

## Troubleshooting Common Setup & Provider Errors

| Error / Symptom | Probable Cause | Corrective Action |
| :--- | :--- | :--- |
| **`503 Service Unavailable`**<br>`"Live LLM mode is not configured"` | `LLM_MODE=live` is set in `.env`, but no valid cloud API key is provided for the selected model. | Set `OLLAMA_API_KEY`, `GEMINI_API_KEY`, etc. in `backend/.env`, or set `LLM_MODE=mock` to test with offline fixtures. |
| **`502 Bad Gateway`**<br>`"The language model request failed"` | Upstream cloud provider rejected request (invalid key, exhausted quota, or network failure). | Verify your API key in the provider console (e.g., Google AI Studio, Ollama Cloud) and test your connection. |
| **`504 Gateway Timeout`**<br>`"The language model timed out"` | Cloud provider did not return tokens within `LLM_TIMEOUT_SECONDS`. | Increase `LLM_TIMEOUT_SECONDS` (e.g., to `90` or `120`) in `backend/.env`. |
| **Web Evidence displays `UNAVAILABLE`** | `TAVILY_API_KEY` is empty, expired, or invalid. | Obtain a valid API key from [tavily.com](https://tavily.com) and add it to `backend/.env`. MetaQA will continue running independently. |
| **CORS error in browser console** | Backend is blocking requests because origin does not match. | Ensure `FRONTEND_ORIGIN=http://localhost:5173` in `backend/.env` matches your browser URL. |
| **Port conflict (8000 or 5173 in use)** | Another background process is occupying the required port. | Stop existing processes on port 8000 (`netstat -ano \| findstr :8000`) or run uvicorn on another port with proxy updates. |

## Research Foundations & Citations

   > *Informs the claim-level verification and authoritative domain categorization.*

## System Limitations

1. **Internal Consistency vs. Physical Reality**: MetaQA tests internal semantic invariance. If a model consistently believes and defends an incorrect premise under all perturbations, MetaQA will classify it as consistent.
2. **Web Retrieval Dependency**: Web Evidence accuracy is bounded by search engine coverage, snippet extraction fidelity, and website access (paywalls/robots.txt).
3. **Evidence Insufficiency**: An `INSUFFICIENT_EVIDENCE` verdict denotes a lack of retrieved data, not affirmative hallucination.
4. **Heuristic Risk Fusion**: The Combined Hallucination Risk is an application-level engineering heuristic designed for user clarity; it is not a calibrated statistical probability.
5. **No Full Live Benchmark Run**: As documented in [`docs/final_results_lock.md`](file:///c:/Users/Rohan/Desktop/mini-project/verifact/docs/final_results_lock.md), the historical 2×2 study was executed with mock fixtures, and the live 2×2 experiment configuration was frozen as not executed due to unconfigured live keys.
