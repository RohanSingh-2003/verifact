# System Architecture

VeriFact is a research-oriented hallucination detection system. It comprises a modern React single-page application, a high-performance FastAPI backend service, an SQLite persistence layer, and a multi-provider LLM abstraction layer.

The core **MetaQA** detection engine is **reference-free** (zero-resource): it evaluates internal answer consistency without web search. VeriFact also runs an independent **Web Evidence** pipeline (Tavily) that checks extracted claims against retrieved snippets. The two signals are not collapsed into one score.

## 1. Frontend Architecture

- **Framework**: React 19, TypeScript, Vite.
- **Styling**: Tailwind CSS (Tailwind v4 with `@tailwindcss/vite`).
- **Icons & Navigation**: `lucide-react`, `react-router-dom`.
- **Pages**:
  - `DetectPage` (`/`): Progressive detection dashboard. As soon as the base answer is generated by Gemma 4:26B, it renders. The client then polls `GET /api/runs/{id}` to display live mutation checks, independent peer verdicts (`IndependentVerdictsCard`), Web Evidence claims and sources, and the final Verification Summary.
  - `HistoryPage` (`/history`): Paginated run history with filtering, search capabilities, and audit traces.
  - `MetaQAPage` (`/metaqa`): Interactive explanation of MetaQA metamorphic methodology, multi-model mutation verifiers, and scoring tables.
  - `WebAnalysisPage` (`/web-analysis`): Educational guide explaining question-type routing, authoritative domain categorization, and evidence consistency scoring.
  - `SettingsPage` (`/settings`): Inspection of active runtime configuration parameters and configured cloud providers.

## 2. Backend Architecture

- **Framework**: FastAPI with Pydantic v2 schemas and validation settings (`pydantic-settings`).
- **Asynchronous Execution**: Uses FastAPI's `BackgroundTasks` to return the candidate answer immediately, then runs **three concurrent background branches** inside one background task via `asyncio.gather(..., return_exceptions=True)`:
  1. `POST /api/detect` accepts the question and invokes Gemma 4:26B to generate the candidate answer.
  2. The initial run is persisted to SQLite with status `answer_ready`.
  3. The response is returned to the client immediately (`overall_status: running`).
  4. Three concurrent verification branches execute in parallel:
     - **Branch 1: MetaQA Pipeline** (`_continue_metaqa_analysis()`): Claims are parsed, Gemma generates synonym/antonym mutations, and the multi-model verifier pool evaluates each mutation concurrently via `multi_verifier.py`.
     - **Branch 2: Direct-Answer Multi-Model Review** (`_continue_independent_verdicts()`): Non-Gemma peer models concurrently evaluate Gemma's full answer against rich context (question, answer, claims, mutations, web snippets) and return structured verdicts, rationales, and contradictory claims.
     - **Branch 3: Web Evidence Pipeline** (`_continue_web_evidence()`): Claims are extracted, Tavily search queries are dispatched, snippets are parsed, claims are verified against retrieved evidence, and the Web Consistency Score is calculated.
  5. When all branches reach a terminal state, `overall_status` becomes `completed` (all succeeded) or `partial` (one or more verification branches encountered errors). Overall `failed` is reserved for missing AI answers.
- **Stage-by-Stage Callbacks (MetaQA)**:
  - `on_stage(stage)`: Records transition (`generating_mutations`, `verifying_mutations`, `calculating_score`).
  - `on_mutations_ready(mutations)`: Saves mutation statements to SQLite with status `mutations_ready`.
  - `on_mutation_verified(position, scored)`: Streams completed verification results into the database as individual mutations finish.
- **Web Evidence stages** progress independently (`classifying_question` → `extracting_claims` → `searching_web` → `verifying_evidence` → `completed` / `failed` / `unavailable`).

## 3. MetaQA Engine (`app.metaqa`)

- **`detector.py`**:
  - Coordinates answer generation, mutation generation, concurrent verification, and score computation.
  - Measures high-resolution stage timings (`answer_ms`, `mutation_ms`, `verify_ms`, `total_ms`).
- **`mutation.py`**:
  - Extracts 3–4 atomic factual claims using `extract_core_claims()`.
  - Generates balanced synonym (meaning-preserving) and antonym (meaning-reversing) mutations.
  - Enforces syntactic heuristics: rejects fragments, incomplete sentences, duplicate phrases, questions, and no-op copies.
  - Partial retry loop: only requests missing mutations across up to 4 rounds rather than throwing away valid ones.
- **`multi_verifier.py`**:
  - Concurrently verifies each mutation statement across the configured multi-model verifier pool (`Gemini`, `GLM-4.7`, `Qwen-2.5`, `Liquid/OpenRouter`).
  - Verifiers receive only the question, candidate answer, and the single mutated statement—never knowing whether the mutation is a synonym or antonym, nor the expected verdict.
- **`verifier.py`**:
  - Parses verdicts: `YES`, `NO`, or `NOT SURE`. Robust fallback converts ambiguous outputs to `NOT SURE`.
- **`scoring.py`**:
  - Evaluates each verdict deterministically:
    - Synonym: `YES` = 0.0, `NO` = 1.0, `NOT SURE` = 0.5
    - Antonym: `YES` = 1.0, `NO` = 0.0, `NOT SURE` = 0.5
  - Aggregates the mean contribution score bounded to $[0.0, 1.0]$.
  - Classifies as **Hallucinated** ($H \ge 0.5$) or **Reliable** ($H < 0.5$).

## 4. LLM Abstraction Layer (`app.llm`)

All LLM clients inherit from the abstract base class `LLMClient` (`complete_text` and `complete_json`):

1. **`OllamaCloudClient`** (`app/llm/providers.py`):
   - Interfaces directly with the official Ollama Cloud API (`https://ollama.com/api`).
   - Forces `think: false` to disable hidden reasoning loops that exhaust token budgets.
   - Dedicated role: Sole answer generator (Gemma 4:26B) and mutation generator.
2. **Multi-Model Verifier Pool** (`app/llm/providers.py`):
   - **`GeminiAdapter`**: Google Gemini Flash 3.8 via official Gemini SDK.
   - **`CloudflareClient`**: GLM-4.7-Flash via Cloudflare Workers AI.
   - **`GroqClient`**: Qwen-2.5-32B via Groq.
   - **`OpenRouterClient`**: Liquid LFM-2.5 via OpenRouter.
   - Dual roles:
     - Internal mutation verification inside MetaQA (`app/metaqa/multi_verifier.py`).
     - Concurrent direct-answer peer review (`app/services/independent_verifiers.py`).
3. **`OpenAICompatibleClient`** (`app/llm/client.py`):
   - Calls OpenAI-compatible chat completion endpoints (`/chat/completions`).
   - Supports exponential backoff and retry handling.
4. **`MockLLMClient`** (`app/llm/mock.py`):
   - Returns deterministic, fixture-based responses for tests and CI without external dependencies.

### Multi-Model Independent Review Rationale

Relying on a single model to both generate and verify factual claims exposes the verification pipeline to self-confirmation bias: models often confirm their own false premises. VeriFact resolves this by enforcing structural separation between answer generation and verification:

- **Dedicated Generator**: Gemma 4:26B generates the base answer and candidate mutations.
- **Multi-Model Verifier Pool**: Independent peer models (`Gemini 3.8 Flash`, `GLM-4.7-Flash`, `Qwen-2.5-32B`, `Liquid LFM-2.5`) evaluate each mutation concurrently without access to the generator's internal states.
- **Direct-Answer Peer Review**: Independent peer models simultaneously examine the generator's full answer against extracted context, surfacing consensus, peer rationales, and contradictory claims.

## 5. Persistence & Storage (`app.database`, `app.services`)

- **Engine**: SQLite via SQLAlchemy ORM (default path `backend/data/verifact.db`).
- **Models**:
  - `Run`: Stores question, generated base answer, generator model, hallucination score, classification, stage timings, overall verification status, and synthesis summary.
  - `MutationRecord`: Stores individual mutation statements, mutation type, verifier model, verdict, contribution, and rationale.
  - `ExperimentRecord` & `ConditionRecord`: Retained as inert database ORM models to preserve database restore verification and backup integrity without requiring destructive schema migrations.

---

## 6. Research Boundary & Parallel Verification

- **MetaQA zero-resource constraint**: MetaQA itself operates without live web retrieval, Google Search, Wikipedia, or RAG.
- **Concurrent Three-Branch Verification**: After the AI answer is generated, MetaQA, Direct-Answer Multi-Model Peer Review, and Web Evidence execute as **independent parallel verification branches**. Any branch may complete, fail, or become unavailable without blocking the others. The AI answer is always displayed independently of verification.
- **Separate scores & heuristic risk card**: MetaQA Hallucination Score, Web Consistency Score, and Multi-Model Verdicts remain strictly independent signals. The UI presents each metric on dedicated cards alongside a heuristic Combined Risk Card; the underlying research scores are never merged or collapsed into an arbitrary percentage. Partial verification is a valid state, and verification failure is not equivalent to hallucination.
